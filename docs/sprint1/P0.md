## 0. Comment travailler sur une tâche P0

1. Le **Navigator+Tester** écrit le ou les tests de la tâche (ils échouent).
2. Le **Driver** code le minimum pour les faire passer, en respectant les signatures ci-dessous.
3. `pytest` en entier → tout est vert (pas seulement le nouveau test).
4. Le Navigator relit le diff ; le **Product Owner** coche les critères CA cités.
5. **Un commit** :
   `feat: <tâche>` ou `test: <tâche>` (Conventional Commits, en français).

Interdits pour l'IA pendant une tâche :
- modifier une signature de ce fichier sans accord de l'équipe ;
- coder une tâche suivante « en avance » ;
- ajouter une dépendance absente de `requirements.txt` ;
- importer FastAPI, `sqlite3` ou `app.db` dans `services/planner.py` ou `services/ics_export.py` ;
- faire une requête HTTP ailleurs que dans `frontend/api_client.py`.

MOTS_PAR_HEURE = 200
PAS_ARRONDI_HEURES = 0.5

    """Nombre de mots d'un texte (séparés par des espaces)."""

## P0-02 — Chapitres depuis un Markdown

- **Fichier** : `backend/app/services/importer.py`
- **Test** : `test_importer.py::test_titres_markdown_deviennent_chapitres` (test 7)
- **Critères** : CA1.1, CA1.2

```python
@dataclass(frozen=True)
class ChapitreImporte:
    titre: str
    nombre_mots: int
    heures: float

def extraire_chapitres_markdown(texte: str, titre_par_defaut: str) -> list[ChapitreImporte]:
    """Découpe un texte Markdown en chapitres : un chapitre par titre # ou ##."""
```

Règles :
- Une ligne est un titre de chapitre si elle commence par **exactement** `# ` ou `## `
  (dièse(s) puis espace). `###` et plus = du contenu normal.
- Le titre = la ligne sans les `#` ni les espaces autour.
- Le contenu d'un chapitre = les lignes jusqu'au titre suivant ; on compte ses mots
  (le titre lui-même n'est **pas** compté) puis `calculer_charge`.
- Le texte **avant** le premier titre est ignoré.
- **Aucun titre** dans le fichier → un seul chapitre nommé `titre_par_defaut`,
  avec tous les mots du texte.
- L'ordre des chapitres = l'ordre du fichier.

Cas du test :

```markdown
Intro ignorée
# Chapitre A
un deux trois
## Chapitre B
### Sous-partie
quatre cinq
```
→ `[ChapitreImporte("Chapitre A", 3, 1.0), ChapitreImporte("Chapitre B", 4, 1.0)]`

Pourquoi 4 mots pour B : `### Sous-partie` est du contenu, et `split()` y voit 2 mots
(`###` et `Sous-partie`), plus `quatre cinq`. « Intro ignorée » n'est compté nulle part.

Le test vérifie aussi qu'un texte **sans titre** (`"un deux trois"`) donne un seul
chapitre nommé `titre_par_defaut`, avec 3 mots.

**Fini quand** : test 7 vert ; `sample_data/SQL.md` donne 5 chapitres.

## P0-05 — Planificateur : priorité et échéances

- **Fichier** : `backend/app/services/planner.py`
- **Tests** : tests 3, 4, 13, 14
- **Critères** : CA3.3, CA3.4, CA3.6, CA3.7, SPEC §5.2

```python
def prochaine_echeance(cours: CoursAPlanifier, jour: date) -> EcheanceAPlanifier | None:
    """L'échéance la plus proche strictement après `jour`, ou None."""

def calculer_score(cours: CoursAPlanifier, jour: date) -> float | None:
    """weight × coef_priorité / jours_restants (min 1). None si aucune échéance à venir."""

def est_eligible(cours: CoursAPlanifier, session: Intervalle, minutes_restantes: int) -> bool:
    """Vrai s'il reste du travail et si la session finit avant le jour de l'échéance."""

def generer_planning(semaine: str, cours: list[CoursAPlanifier],
                     disponibilites: Disponibilites,
                     creneaux_occupes: list[Intervalle],
                     maintenant: datetime) -> list[SessionPlanifiee]:
    """Place les sessions de la semaine, de façon gloutonne, par score décroissant."""
```

Algorithme (glouton, **à respecter tel quel**) :
1. Calculer les créneaux libres (P0-04), les découper en sessions candidates, triées
   par début.
2. Garder une copie modifiable des `minutes_restantes` de chaque chapitre.
3. Pour **chaque session candidate**, dans l'ordre chronologique :
   - garder les cours **éligibles** : il reste des minutes à un de leurs chapitres, et
     s'ils ont une échéance à venir, `session.fin <= datetime.combine(echeance.date, time(0, 0), FUSEAU)` ;
   - les cours **avec** score passent avant ceux **sans** score ;
   - parmi les cours avec score : score le plus haut ; à égalité, `id` le plus petit ;
   - parmi les cours sans score : `COEF_PRIORITE` le plus haut ; à égalité, `id` le plus petit ;
   - aucun cours éligible → la session candidate reste vide ;
   - sinon : prendre le **premier chapitre** du cours (dans l'ordre) qui a encore des
     minutes, créer la `SessionPlanifiee`, retirer `minutes_session` à ses minutes restantes.
4. Renvoyer la liste (ordre chronologique).

Règles de calcul :
- `jours_restants = max(1, (echeance.date - jour_de_la_session).days)`.
- `score = echeance.poids * COEF_PRIORITE[cours.priorite] / jours_restants`.
- L'échéance prise en compte est la prochaine **strictement après** le jour de la
  session : le jour même d'une échéance, on ne révise plus pour elle (CA3.3).
- Un cours **sans aucune** échéance est planifié en dernier (CA3.6).
- Un cours dont **toutes** les échéances sont passées (ou tombent le jour de la session)
  n'est **plus planifié** : son examen est fini.
  *(Corrigé pendant P0-05 : la 1re version le traitait comme « sans échéance », ce qui
  aurait planifié des révisions après l'examen et contredisait le test 3.)*

Tests (données : fixture de P0-04 + cours supplémentaires) :
- **Test 3** `test_aucune_session_apres_echeance` : cours avec échéance le
  `date(2026, 11, 18)` (mercredi) → aucune session ce mercredi ; les sessions du lundi existent.
- **Test 4** `test_cours_prioritaire_place_en_premier` : deux cours `"medium"` ;
  A (`id=1`) échéance `date(2026, 11, 21)` poids 50 ; B (`id=2`) échéance
  `date(2026, 11, 26)` poids 50. 1re session = lundi 16/11 18:00 : score A = 50/5 = 10,
  B = 50/10 = 5 → **la 1re session est pour A**.
- **Test 13** `test_priorite_haute_multiplie_le_score` : exemple 1 de SPEC §5.2 —
  A (`id=1`, `"high"`) échéance `date(2026, 11, 26)` poids 60 → 60 × 2 / 10 = 12 ;
  B (`id=2`, `"medium"`) échéance `date(2026, 11, 20)` poids 30 → 30 × 1 / 4 = 7,5
  → **la 1re session est pour A**, bien que B soit plus proche.
- **Test 14** `test_cours_sans_echeance_planifie_en_dernier` : cours X (`id=1`, `"high"`,
  **sans** échéance, 600 min) et cours Y (`id=2`, `"low"`, échéance `date(2026, 12, 18)`
  poids 10, **120 min** seulement). Résultat attendu : les **2 premières** sessions sont
  pour Y (il a un score, X n'en a pas), les sessions **suivantes** sont pour X
  (Y n'a plus de minutes) → X est planifié, mais en dernier.

**Fini quand** : tests 1 à 6, 13, 14 verts ; `planner.py` n'importe ni FastAPI ni sqlite3.

Règles :

- Chaque `VEVENT` : `UID = f"session-{id}@helpstud"`, `SUMMARY = f"{cours} — {chapitre}"`,
  `DTSTART` / `DTEND` = heures **converties en UTC** (`.astimezone(timezone.utc)`),
  `DTSTAMP = maintenant` en UTC.
- Pourquoi UTC : tous les agendas convertissent l'UTC sans ambiguïté (SPEC §10).
- Liste vide → un calendrier valide sans `VEVENT`.

Tests :
- **Test 9** `test_ics_valide_un_vevent_par_session` : 2 sessions → `Calendar.from_ical(...)`

CREATE TABLE IF NOT EXISTS courses (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  priority TEXT NOT NULL DEFAULT 'medium' CHECK (priority IN ('high','medium','low')),
  category TEXT CHECK (category IN ('exam','continuous','mixed'))
);
CREATE TABLE IF NOT EXISTS chapters (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id INTEGER NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  position INTEGER NOT NULL,
  title TEXT NOT NULL,
  hours REAL NOT NULL
);
CREATE TABLE IF NOT EXISTS deadlines (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id INTEGER NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  type TEXT NOT NULL CHECK (type IN ('exam','assignment')),
  date TEXT NOT NULL,                       -- AAAA-MM-JJ
  weight INTEGER NOT NULL CHECK (weight BETWEEN 0 AND 100)
);
CREATE TABLE IF NOT EXISTS availability (
  id INTEGER PRIMARY KEY CHECK (id = 1),    -- une seule ligne : un seul utilisateur
  session_minutes INTEGER NOT NULL,
  slots_json TEXT NOT NULL                  -- {"monday": ["18:00-20:00"], ...}
);
CREATE TABLE IF NOT EXISTS sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id INTEGER NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  chapter_id INTEGER NOT NULL REFERENCES chapters(id) ON DELETE CASCADE,
  start_at TEXT NOT NULL,                   -- ISO 8601 avec décalage
  end_at TEXT NOT NULL,

);

## P0-10 — Routes planning, sessions et .ics

- **Fichier** : `backend/app/routers/plan.py`
- **Critères** : CA3.1 à CA3.8, CA4.1 à CA4.3, CA5.3

`POST /plan/generate` `{week}` — étapes **dans cet ordre** :
1. Calculer `[lundi 00:00, lundi suivant 00:00)` de la semaine (Europe/Paris).
2. Supprimer les sessions **non faites** de cette semaine (CA3.7).
3. Pas de disponibilités enregistrées → renvoyer `[]`.
4. `creneaux_occupes` = sessions **faites** de cette semaine (elles gardent leur place).
5. Pour chaque chapitre : `minutes_restantes = hours × 60 − durée de toutes ses sessions
   restantes en base` (faites, ou planifiées dans d'autres semaines) ; minimum 0.
6. Construire les `CoursAPlanifier` (chapitres dans l'ordre `position`, échéances du cours).
7. Appeler `planner.generer_planning(week, cours, disponibilites, creneaux_occupes, maintenant)`
   avec `maintenant = datetime.now(FUSEAU)`.
8. Insérer les nouvelles sessions ; renvoyer **toutes** les sessions de la semaine
   (faites + nouvelles), triées par `start`.

| Route | Comportement |
|---|---|
| `GET /plan?week=…` | Sessions dont le début est dans la semaine, triées par `start`. Filtrer **en Python** après `datetime.fromisoformat` (comparer des textes ISO avec des décalages différents donne des erreurs au changement d'heure). |
| `PATCH /sessions/{id}` `{done}` | Met `done` à 0/1 (on peut revenir en arrière) ; inconnue → **404** ; **200** + `Session`. |
| `GET /plan.ics` | Toutes les sessions + noms des cours et titres des chapitres → `ics_export.exporter_ics` → `Response(content, media_type="text/calendar")` avec l'en-tête `Content-Disposition: attachment; filename="helpstud.ics"`. |

**Fini quand** : les 4 routes répondent selon le contrat ; une génération relancée ne
duplique pas les sessions non faites.
